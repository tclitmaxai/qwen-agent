# qwen-agent

Автономный «инженерный агент» на локальной модели: ноутбук превращает Qwen3.8-27B abliterated (GGUF UD-Q4_K_XL, llama.cpp / `llama-server` на Kaggle T4 x2) в инженера, который сам решает issues в GitHub-репозитории.

## Файлы

| Файл | Назначение |
|---|---|
| `qwen38_repo_agent2.ipynb` | Основной ноутбук (актуальная версия): агент с push веток и открытием pull request |
| `qwen38_repo_agent1.ipynb` | Предыдущая версия ноутбука (без push/PR — только патчи и комментарии) |
| `qwen38_model_capabilities.txt` | Шпаргалка по возможностям модели (по версии agent1) |
| `GITHUB_TOKEN.md` | Заметка: как создать токен `GITHUB_TOKEN` |

## Что умеет агент (qwen38_repo_agent2.ipynb)

1. **Модель и сервер.** Скачивает модель с Hugging Face (или берёт из подключённого Kaggle-Dataset) и собирает/запускает `llama-server` с CUDA; автоматически подбирает размер контекста (до 262 144 токенов) и тип KV-кэша (q8_0/q4_0), пока модель не поместится в память двух T4. OpenAI-совместимый API: чат со стримингом, режим рассуждений `deepseek`, настраиваемая температура и лимит выходных токенов.
2. **Очередь issues.** Клонирует репозиторий в `/tmp` и читает все issues через GitHub API: сначала по приоритету (`priority:p0`, `p1`, `p2`, потом остальные), внутри приоритета — по номеру.
3. **Решение задач инструментами.** Для каждого issue берётся ветка `agent/issue-N-короткое-название`: если такая (по номеру) уже есть в GitHub — продолжается с неё, иначе создаётся от базовой. Модель вызывает инструменты текстовым протоколом `@@CALL/@@ARG/@@END`:
   - изучение кода: `list_files`, `search_code`, `read_file`;
   - правки: `patch_file` (точечные изменения), `write_file` (новые файлы), `delete_file`;
   - проверки: `run_command` (тесты и скрипты локально; лимиты 300 с на команду и 900 с на issue), `run_in_codespace` (облачная среда GitHub Codespaces, если локально проверить нельзя — правки переносятся в неё автоматически, без push);
   - контроль изменений: `git_diff`, `commit`;
   - коммуникация: `comment_issue` (вопросы людям по ходу работы, лимит на issue), `create_issue` (новые issues с приоритетом `p0/p1/p2` и меткой `qwen-agent`, защита от дубликатов — в том числе закрытых issues);
   - отчётность: `report_work` (финальный отчёт «Сделано / Не сделано / Проверка») и `report_no_action_needed` (обоснование, что правка не нужна — его проверяет модель-ревьюер).
4. **Раунды и бюджет.** Работа идёт раундами (по умолчанию до `STEPS_PER_ROUND = 14` вызовов за раунд и до `MAX_ROUNDS = 4` раундов на issue); каждый раунд — новый чат с «проверенными системой» фактами из git, поэтому контекст не разрастается.
5. **Зачёт.** Решение засчитывается только если есть реальный diff и принят финальный отчёт («нет коммитов — нет зачёта»).
6. **Push и pull request (новое в agent2).** При итогах `solved`/`partial` система сама делает `git push` в ветку `agent/…` (без `--force`, только ветки с префиксом `BRANCH_PREFIX`, базовая ветка — никогда) и открывает pull request: по умолчанию черновик с `Closes #N`, для `partial` — с пометкой `[WIP]` и `Refs #N`. Если PR для ветки уже есть, обновляется его описание. Сам агент `git push` и `gh` вызвать не может.
7. **Комментарии и отчёт.** При итогах `solved`/`partial` в issue публикуется отчёт агента (со ссылкой на PR; патч прикладывается, только если push не удался). Повторный запуск обновляет тот же комментарий (маркер), а не плодит новые. В конце прогона — `agent_report.md` (что сделано, что не удалось и почему, какие комментарии и issues созданы), патчи `patches/issue-N.patch` и трассы `traces/issue-N.jsonl`.

## Чего агент НЕ делает

- Не пушит в базовую ветку, не использует `--force`, не сливает pull request (слияние — только вы).
- Записи в GitHub: только ветки `agent/…`, pull request, комментарии, новые issues и временный Codespace (останавливается в конце прогона; тратит вашу квоту Codespaces).
- «Самопроверка» (JUDGE) — мнение той же модели: ориентир, а не гарантия.

## Режимы работы (настройки в ноутбуке)

| Настройка | Что делает |
|---|---|
| `GITHUB_PUSH = False` | Без веток и PR: только патч и комментарий |
| `GITHUB_WRITE = False` | Вообще без записи: комментарии и новые issues сохраняются черновиками в `agent_out/drafts/` |
| `PR_DRAFT = False` | PR открывается обычным, не черновиком |
| `ISSUE_LIMIT = N` / `ONLY_ISSUES = [...]` | Ограничить очередь (удобно для пробного прогона) |
| `RERUN_DONE = True` | Заново решать уже обработанные issues |
| `MAX_TOTAL_SEC` | Не начинать новые issues после этого времени |

## Запуск

1. Kaggle: GPU T4 x2, Internet On.
2. (Рекомендуется) подключить Dataset с бинарником `llama-server` и моделью — иначе ноутбук соберёт llama.cpp из исходников и скачает модель с Hugging Face.
3. Создать и добавить токен: см. [GITHUB_TOKEN.md](GITHUB_TOKEN.md) (в Kaggle: Add-ons → Secrets → `GITHUB_TOKEN`).
4. В ноутбуке указать `GITHUB_OWNER` / `GITHUB_REPO` (при необходимости `BASE_BRANCH`, `ISSUE_LIMIT`, `ONLY_ISSUES`).
5. Сначала запустите ячейку проверки: `check_token_access()` без побочных эффектов (пустые запросы и `git push --dry-run`) покажет, какие права реально есть у токена (Issues, Pull requests, Contents), и выведет очередь issues.
6. Запустите агента. Если сессия оборвётся — запустите ячейку снова: уже обработанные issues пропускаются (`results.json`).

Для публичного репозитория без записи токен не обязателен (но действует лимит 60 запросов/час без аутентификации).

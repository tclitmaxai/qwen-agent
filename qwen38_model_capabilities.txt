ВОЗМОЖНОСТИ НЕЙРОСЕТЕВОЙ МОДЕЛИ С ПОМОЩЬЮ НОУТБУКА qwen38_repo_agent1.ipynb

Ноутбук превращает локальную языковую модель (Qwen3.8-27B abliterated, GGUF UD-Q4_K_XL,
запущенная через llama.cpp / llama-server на Kaggle T4 x2) в автономного
инженерного агента, который сам решает issues в GitHub-репозитории.

1. ЗАПУСК И НАСТРОЙКА МОДЕЛИ
   - Скачивает модель с Hugging Face (или берёт из подключённого Kaggle-Dataset)
     и собирает/запускает llama-server с CUDA.
   - Автоматически подбирает размер контекста (до 262 144 токенов) и тип
     KV-кэша (q8_0/q4_0), пока модель не поместится в память двух T4.
   - Подключает OpenAI-совместимый API (чат со стримингом, режим рассуждений
     "deepseek", настраиваемая температура и лимит выходных токенов).

2. АВТОНОМНАЯ РАБОТА С GITHUB-РЕПОЗИТОРИЕМ
   - Клонирует указанный репозиторий локально и читает все issues через
     GitHub API, расставляя их по приоритетам (сначала priority:p0, p1, p2,
     затем остальные) и по номеру.
   - Для каждого issue создаёт отдельную локальную ветку agent/issue-N и
     решает его последовательно.

3. ИНСТРУМЕНТАЛЬНОЕ РЕШЕНИЕ ЗАДАЧ (model tool calling)
   Модель сама выбирает и вызывает инструменты в текстовом протоколе
   @@CALL/@@ARG/@@END:
   - изучение кода: list_files, search_code, read_file;
   - правки: patch_file (точечные изменения), write_file (новые файлы),
     delete_file;
   - проверки: run_command (запуск тестов и скриптов локально, лимиты 300 с
     на команду и 900 с на issue), run_in_codespace (облачная среда GitHub
     Codespaces, если локально проверить нельзя — правки переносятся
     автоматически, без push);
   - контроль изменений: git_diff, commit;
   - коммуникация: comment_issue (вопросы людям по ходу работы, с лимитом на
     issue), create_issue (новые issues с приоритетом p0/p1/p2 и меткой
     qwen-agent, с защитой от дубликатов, включая закрытые);
   - отчётность: report_work (финальный отчёт «Сделано / Не сделано /
     Проверка») и report_no_action_needed (обоснование, что правка не нужна).

4. ОРГАНИЗАЦИЯ РАБОТЫ И КОНТРОЛЬ КАЧЕСТВА
   - Работа ведётся раундами (до 14 вызовов инструментов за раунд, до 4
     раундов на issue); каждый раунд — новый чат с «проверенными системой»
     фактами из git, поэтому контекст не разрастается.
   - Решение засчитывается только при реальном diff и принятом финальном
     отчёте («нет коммитов — нет зачёта»).
   - Самопроверка: та же модель в роли ревьюера (JUDGE) оценивает решение и
     обоснования «правка не нужна».
   - При итогах solved/partial система публикует отчёт с патчем в issue
     (повторный запуск обновляет тот же комментарий, а не плодит новые).
   - В конце прогона формируются отчёт agent_report.md (что сделано, что не
     удалось и почему, какие комментарии и issues созданы) и патчи
     patches/issue-N.patch.

5. ЧТО МОДЕЛЬ НЕ ДЕЛАЕТ (безопасные границы)
   - Не выполняет git push и не создаёт Pull Request.
   - Не меняет код в удалённом репозитории напрямую: записи в GitHub — только
     комментарии, новые issues и временный Codespace.
   - Есть режим без записи (GITHUB_WRITE = False): комментарии и новые issues
     сохраняются черновиками в agent_out/drafts/, ничего не отправляясь в
     GitHub.

ИТОГО: с помощью этого ноутбука нейросетевая модель может самостоятельно
принимать issues из репозитория, читать и понимать код, вносить исправления,
запускать тесты (локально и в Codespaces), коммитить изменения, публиковать
отчёты и новые issues — то есть выполнять роль автономного junior-инженера
по закрытию задач, не трогая основную ветку репозитория.
